# 仓库工程化与开源治理策略

T2（仓库工程化）的决策记录。一期收口时 T2 已部分落地但未经讨论，2026-09-11 项目主要求回炉——本文是回炉 grill 会话（两轮 15 题）的定案，补上当时缺失的决策文档。范围：部署策略、供应链加固、分支纪律、许可细节、对外文案防线、社区治理文件、issue 体系、版本与发布机制。

## 决定（15 项）

### A. 发布与部署

1. **部署触发：一二期维持"推 main → CI 全绿 → 自动发布 GitHub Pages"，T12 分发定案时切换为"打 tag 才发布"。** deploy 任务 `needs: check-build`，坏提交不可能上线；一二期处于"软上线"状态（URL 可访问但不宣传），换取真机验收随时有最新版可测。T12 后 URL 对外、家庭在用，届时版本纪律优先。
2. **README 发布地址与仓库主页链接，待真机验收 + DevTools 零请求复核通过后回填**——验收标准是准绳，未验收不宣传。
3. **版本与发布机制**：`0.x = 期序号`（0.1 = 开发一期，0.2 = 二期），`1.0` = 机构验证结论回填 + T12 分发定案之后。每期收口（验收全过）打 `v0.x.0` tag + GitHub Release，Release 说明 = devlog 摘要 + 验收清单勾选记录；devlog 全文进 `docs/devlog/`，**该目录纳入禁语扫描**（devlog 是对外传播文案）。不另维护 CHANGELOG——Release 页即变更史，单人项目不双写。

### B. 供应链与 CI

4. **CI 中所有 GitHub Actions 钉全长 commit SHA**（注释保留版本号），更新走每期收口人工核对，不引入 dependabot。依据：tj-actions 事件（CVE-2025-30066，2025-03，2.3 万仓库受害）即 tag 被整体重指到恶意提交；GitHub 官方安全指引推荐 SHA pinning，2025-08 起平台支持强制该策略。对星屿的特殊分量：**部署链路完整性 = "零收集可查证"承诺的上游**——deploy 路径被投毒则家庭加载的不是仓库里审计过的代码。规矩写进 ci.yml 注释：今后任何第三方 action 必须钉 SHA。与 ADR-0005 决定 8 的"每期收口集中升级"节奏同构。
5. **CI 工程杂项**：`concurrency` 组防 Pages 部署重叠；两个 job 各设 `timeout-minutes: 10` 防卡死耗配额；`package.json` 声明 `engines.node >= 20.19` + 根目录 `.nvmrc`（22，与 CI 一致）防贡献者用老 Node 得到不一致行为。

### C. 分支纪律

6. **main 分支设最小保护 ruleset：禁删除 + 禁强推，bypass 名单留空；不启用 required status checks。** 日常仍直推 main，CI 事后跑。这道闸防的是"手滑 force push 改写公开历史"——可查证是星屿的信任基石；真需要改写时手动关规则的那几秒正是刹车。**T12 对外分发后升级为全 PR 流**（那时 main = 生产线）。
   记录在案：PR 流程**不是**"未讨论就落实"问题的解药（那个解药是动工前 grill，见下 §F）；PR 挡的是代码坏了，而代码坏了 CI 已经挡住不上线。

### D. 许可

7. **LICENSE 版权行改为 `Copyright (c) 2026 HardyLiu6 and Starry Isle contributors`。** MIT 唯一实质义务是保留此行，它将永远跟随代码；具名初始著作权人便于将来主张权利，对家长与机构也是"有人负责"的可信度加分，且 GitHub ID 本就公开，无新增身份暴露。
8. **LICENSE 恢复逐字标准 MIT 文本**，删除原先插入正文的"素材另行授权"说明段。实测依据：GitHub 许可证识别对该文件返回 `Other / NOASSERTION`，仓库页不显示 MIT 徽识、合规扫描工具读为"未知许可"。同样的说明 README 与 CREDITS.md 已有，LICENSE 内属冗余。
9. **自制素材维持 CC BY-SA 4.0。** 代码 MIT 已接受"可被商用闭源 fork"的代价（换取低协作门槛），素材 SA 是防"换皮收割"的第二道锁：改编星屿美术者必须继续开放。著作权人随时可在 SA 之外另行授权，SA 只约束默认规则。
10. **NC（非商业）素材政策：允许进库，但必须隔离。** 采用时置于独立目录（`public/assets/nc/<来源>/`）+ CREDITS.md 单独标注 + README 许可节声明"含 NC 素材的整体分发不得商用"。目的是把 AAC 生态协作的门开到最大：ARASAAC（12,909 图符，CC BY-NC-SA，全球特教事实标准）在二期社交故事玩法中可用。代价记录在案：NC 的"非商业"边界模糊（机构把星屿预装进收费课程平板是否算商用属灰区），且 NC 传染整体分发，fork 者的商用自由被切掉一块。
    **同类需求仍优先选无 NC 的来源**——Mulberry Symbols（3,116 图符，CC BY-SA）是首选兜底。勘误：总体规划 T2 原文"ARASAAC/Mulberry 的 NC 条款"有误，Mulberry 为 CC BY-SA，不含 NC（2026-09-11 核验官方源）。

### E. 对外文案防线

11. **建立"仓库外对外文案清单"并写进 CONTRIBUTING 措辞红线。** 禁语脚本只扫仓库内文件，够不到 GitHub About 描述、topics、Release 说明、社交预览图、未来应用商店文案——而这些是传播链路上最先被看到的字。规定：改动这些表面前对照研 04 措辞清单人工过一遍。
12. **仓库 About 与 topics 即刻填写**（仓库门面空着损害可信度）。About 定稿："公益、免费、开源的儿童情绪认知辅助训练应用——面向孤独症谱系儿童家庭，家长共玩，零数据收集，纯静态本地运行"（已过禁语自查）；topics：`autism`、`accessibility`、`education`、`kids`、`react`、`static-site`。
13. **免责声明"三处同文"改为单一来源 + 机器校验。** 声明文本抽到 `src/disclaimer-text.ts`（段落数组），组件渲染它；校验脚本核对 README 声明块与之逐段一致，进 `npm run check`。原先的人工注释提醒是最易腐烂的约定，而三处同文是合规姿态的组成部分；第三处（家长说明页/发布页）出现时自动纳入同一来源。

### F. 社区治理与 issue 体系

14. **社区健康文件：SECURITY.md、PR 模板、两个 issue 表单（报告问题 / 想法与建议）+ 保留空白 issue 入口、CODE_OF_CONDUCT.md（Contributor Covenant 3.0 简体中文版）——一期上齐；FUNDING.yml 暂不设。**
    - **SECURITY.md**：首选渠道为 GitHub 私密漏洞上报（GHSA，报告者无需知道任何邮箱，开关已开启）。"漏洞"范围明写三类：①依赖/构建链投毒 ②产物运行时发出任何非自身静态资源的请求（直接违背零收集承诺）③家长导入 JSON 进度（二期）相关的注入/XSS。支持范围仅最新发布版；响应写"尽力而为，通常一周内回应"，**不承诺 SLA**——诚实优于漂亮。
    - **issue 表单**：报告问题表单固定提示"请不要上传孩子的照片、姓名或其他个人信息"——issue 区公开，而本项目用户群最经不起这种意外暴露，这与零收集承诺是一体两面。**表单不对报告者施加禁语约束**（那是项目对外文案的规矩，不是对来提意见的家庭的）；保留空白入口，不给不会填表的家长设门槛。
    - **CoC**：面向弱势群体的项目，行为准则分量高于一般项目——issue 区会有孤独症孩子的家长出没，一条羞辱性评论的杀伤远超普通技术仓库；有公示的 CoC，删评/封禁依据的是条款而非维护者心情。采用 Contributor Covenant 3.0（2025-07 发布）官方简体中文译本，保留其分级处理阶梯，另加三条星屿补充约定（禁止扩散儿童可识别信息、禁止贬损性框架谈论孤独症人士、禁止推销"根治"类产品）。如实公示两项局限：单人维护不承诺服务等级；举报若指向维护者本人，项目内无申诉层级，指引改走 GitHub 官方举报渠道。
    - **FUNDING 暂不设**：研 03 结论是家长对"免费但另有所图"高度警惕，赞助按钮是最直白的"所图"信号；将来若需可持续资金，走机构挂靠 + 账目透明再议。
    - 不上：SUPPORT.md（README 已覆盖）、CODEOWNERS（单人无意义）、GOVERNANCE.md（社区化之后再说）。
15. **issue 体系收尾**：5 个 triage 标签（`needs-triage`/`needs-info`/`ready-for-agent`/`ready-for-human`/`wontfix`）已在远端，补一个 `backlog`；删除单人维护用不上的默认噪音标签 `duplicate`/`invalid`/`question`；保留 `good first issue`/`help wanted`（GitHub 全站检索新贡献者的入口，与"社区化对抗单点维护死亡"对策一致）。建里程碑「开发二期」（收 #1–#6）与「机构验证期」（收 #7）。后续期 backlog 七项**不建 issue**，规划文档已记录，进入相应期再转，避免 issue 库未开工先膨胀。**PR 不作为需求入口**（外部 PR 不当 feature request 分诊，记录在 `docs/agents/issue-tracker.md`）——单人维护下的降噪默认。**GitHub Discussions 暂不开启**：多一个要照看的地方就是多一份耗竭风险（风险表"单人精力耗竭"），issue + 建议表单已能承接家长的话；等出现第二个稳定贡献者再开。

## Considered Options

- **打 tag 才发布 / 手动触发（一二期即用）**：开发期每次真机验收都要打 tag，繁琐且无收益（坏版本本就上不了线），推迟到 T12。
- **维持 actions 的可变 tag 引用**：等于赌官方 org 不失守；钉 SHA 成本≈零，拒绝赌。
- **钉 SHA + dependabot（只管 actions 生态）**：单人项目的 PR 噪音 > 收益，与既定"不开自动升级"节奏冲突，拒绝。
- **一期即上全 PR 流 + required checks**：每次变更多一道手续，而它解决不了真正的问题（方向性把关），推迟到 T12。
- **自制素材用 CC BY / CC0**：放弃反圈占保护，与公益定位不符，拒绝。
- **一律拒绝 NC 素材（整库永久可商用再分发）**：许可叙事最纯净，Mulberry 兜底使代价可承受（图符少四分之三、画风选择少）——grill 中与"允许+隔离"并列为价值观题，项目主选择素材余地最大化。
- **免责声明用 diff 脚本比对两处现文**（不改代码结构）：治标，第三处出现时问题重演，拒绝。
- **CoC 不设联系邮箱、只写"通过 GitHub 私信"**：GitHub 无私信功能，对举报违规不是可靠通道，拒绝。
- **开启 Discussions**：见决定 15。

## Consequences

- 供应链的两端都已收紧：npm 侧（lockfile + `npm ci` + 运行时依赖准入三问，ADR-0005 决定 8）与 CI 侧（SHA pinning）；"DevTools 复核零请求"验收从此有构建链完整性背书。
- 许可故事变为三层：代码 MIT（宽松换协作）/ 自制素材 CC BY-SA（反圈占）/ 未来 NC 素材隔离目录（可用但限制整体商用分发）。README 许可节与 CREDITS.md 须随 NC 素材首次入库同步更新。
- 免责声明从"三份人工同步的副本"变为"一份源 + 校验"，`npm run check` 覆盖面从措辞/类型/逻辑扩展到合规文本一致性。
- 治理文件齐备后，仓库对潜在接手人的可读性提高（对抗单点维护死亡的一环）；代价是维护者多了 CoC 执行与安全响应两项责任，故响应承诺刻意写得保守。
- **项目公开身份 = `starry-isle@outlook.com`**（2026-09-11 项目主定，取代原先的 GitHub noreply 止损方案）。它同时承担三个角色：本项目今后的 git 提交署名、CoC 举报渠道、SECURITY.md 的邮件兜底。相比 noreply 地址的优势：**可联系**（noreply 只能发不能收，无法承担 CoC 举报）且**可随项目移交给接手人**——与"降低接续门槛、对抗单点维护死亡"同向；相比个人邮箱的优势：维护者的私人邮箱不再随提交历史扩散。已推送历史中的个人邮箱不作处理（重写历史与 main 禁强推规则冲突，收益不抵成本）。
