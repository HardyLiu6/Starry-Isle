# 09 · 素材管线工程实践：溯源、钉版、许可边界与校验

- **调研日期**：2026-09-23 至 2026-09-24（端点实测时间戳见各节与附录）
- **调研用途**：为 T3 素材管线回炉（"每个素材文件能被脚本回答：来自哪里 / 什么许可 / 有没有被改过"）提供工程事实。已定案方向不在本文重新讨论：删除现有 24 个手工入库 SVG、改由拉取脚本从钉死版本的上游重取且产物进仓库；接口按 150–300 个素材设计；暂不做 sprite/SVGO/分包；自制素材抽成 `public/assets/original/*.svg`（CC BY-SA 4.0）；AI 生图产物只能靠哈希钉住并记录生成元数据；零新增运行时依赖。
- **检索口径**：只认一手来源（规范原文、许可证原文、上游仓库文件、官方文档）。可实测的事项全部实测：GitHub 端点用 `curl -sL -w "%{http_code}"` 与已认证的 `gh api`；哈希一律 `sha256sum < 文件`（从标准输入读，避免 Windows 路径转义污染输出）；本地测试在 `$TEMP` 下的隔离目录进行；仓库内只执行了 `npm ci`、构建（产物在已忽略的 `node_modules/`、`dist/`）与只读 git 命令，除本文外未改动任何受版本控制的文件。标"（推断）"的是本文作者的推断，不是来源原文。

## 给决策者的摘要（≤300 字）

钉版有实际意义：OpenMoji 14→15 同码点字节有变且有可见改动，15→17 未变。现有 24 个文件与上游逐字节相同，"未修改"属实，但事后只能反推版本区间，版本须在拉取时记入 manifest。CC 4.0 要求标明修改，不以构成改编为前提：SVGO、sprite 改字节，应标注。部署产物零署名，仅靠 CREDITS.md 不够，宜设应用内离线署名页。未修改的 BY-SA 文件与 MIT 代码并列属汇编，不传染。REUSE 无 Node 实现、缺来源/版本/哈希字段，宜以自有 manifest 为准；Node 22 可零依赖拉取与校验。暗坑：`.gitattributes` 会把 CRLF 上游改成 LF；默认重编码会剥掉 AI 图元数据。

## 一、REUSE 规范：无法加文件头的素材如何声明

依据 REUSE Specification 3.3（2024-11-14），[reuse.software/spec-3.3](https://reuse.software/spec-3.3/)。

### 1.1 无法加文件头的素材怎么声明

| 规则 | 原文 |
|---|---|
| 覆盖范围 | "Each Covered File MUST have Licensing Information associated with it. You can associate Licensing Information with a file in the following ways: Comment headers / REUSE.toml / DEP5 (deprecated). REUSE.toml and DEP5 are mutually exclusive. … Comment headers are the RECOMMENDED method." |
| 文件分类 | "Commentable File — a plain text file that can contain comments. Uncommentable File — either a plain text file that cannot contain comments or a file that is not a plain text file." |
| `.license` 伴随文件 | "For Uncommentable Files, the comment header that declares the file's Licensing Information MUST be in an adjacent text file of the same name with the additional extension `.license` (example: `cat.jpg.license` if the original file is `cat.jpg`)." |
| `.license` 优先 | "If a Commentable File contains Licensing Information but also has an adjacent `.license` file, then the Licensing Information defined in the `.license` file takes precedence, and the Commentable File's contents are ignored." |
| REUSE.toml 位置与版本 | "A `REUSE.toml` file MAY be located in any directory, and can cover files that are within its directory or deeper."；"The `version` key (REQUIRED) MUST have an integer value … This specification describes version 1 of REUSE.toml." |
| `[[annotations]]` 键 | `path`（REQUIRED，字符串或列表，可用 `*`/`**` 通配，必须用正斜杠）；`precedence`（OPTIONAL）；`SPDX-FileCopyrightText`（OPTIONAL）；`SPDX-License-Identifier`（OPTIONAL，须为合法 SPDX 许可表达式） |
| `precedence` 三个值 | `closest`（默认）："associate the Licensing Information inside of the Covered Files (or its adjacent `.license` file), if available"；`aggregate`："always associate the Licensing Information defined in the table with the table's Covered Files. Subsequently, the `closest` logic is also applied"；`override`："associate the Licensing Information defined in the table … and to ignore any other Licensing Information that is closer" |
| 同一文件命中多张表 | "exclusively the last matching table in the file is used for that Covered File" |
| 许可全文 | "Each License File MUST be placed in the `LICENSES/` directory in the root of the Project. The name of the License File MUST be the SPDX License Identifier of the license followed by an appropriate file extension"；不在 SPDX 列表的许可用 `LicenseRef-[idstring]` |
| DEP5 | "you SHOULD create a `REUSE.toml` file instead. The DEP5 file is deprecated" |

对 SVG（Commentable File）：规范推荐写注释头，但往上游 SVG 里加注释就改了字节，与"字节 = 上游"冲突；（推断）应走 `.license` 伴随文件或 REUSE.toml，不碰素材本身。

### 1.2 有没有字段能记"来源 URL / 版本"

规范原文："You MAY include other keys and tables to convey additional information. Their semantics are not defined by this specification. If you wish to include other keys, you are RECOMMENDED to use existing SPDX tags. For example, you could use `SPDX-FileComment` in an `[[annotations]]` table to add context to what you're doing, or `SPDX-FileContributor` to credit additional contributors."

SPDX 2.3 对这两个字段的定义：File comment "provides a place for the SPDX document creator to record any general comments about the file"；File contributor "provides a place for the SPDX document creator to record file contributors. Contributors could include names of copyright holders and/or authors who might not be copyright holders"（[SPDX 2.3 File information](https://spdx.github.io/spdx-spec/v2.3/file-information/)）。

即：REUSE **没有**专门记录来源 URL、上游版本、哈希、是否修改的字段；`SPDX-FileComment` 可以塞一段自由文本，但规范明言其语义未定义。SPDX 文档格式本身有 File checksum 字段（"sensitive to changes in the file's data"）；（推断）那是 SBOM 输出里的"计算值"，不是可被核对的"期望值"。

### 1.4 REUSE 与项目自有 manifest 的取舍（推断）

| 维度 | REUSE | 自有 manifest JSON |
|---|---|---|
| 三问覆盖 | 只答"什么许可 / 谁的版权"；来源、版本、是否修改没有定义字段 | 可以把三问（加 AI 生成元数据）放进同一条记录 |
| 覆盖面 | 规范要求**仓库里每个 Covered File**（含全部源码）都有许可信息，外加 `LICENSES/` 目录放全文 | 只管 `public/assets/**` |
| 校验工具 | Python，CI 要多一条工具链（pip 或 Docker） | Node 零依赖脚本，与现有 `check:*` 同构 |
| 外部认可 | 标准格式，合规扫描工具（ScanCode、ORT 等）能读 | 只有本项目认识 |
| 双账风险 | 若两者并存且都手写，许可会记两遍 | — |

可兼得的做法（推断）：manifest 作为唯一来源，必要时由脚本**生成** REUSE.toml（每条写 `path`、`SPDX-FileCopyrightText`、`SPDX-License-Identifier`，再用 `SPDX-FileComment` 放 "source@ref sha256"），像免责声明那样"一份源 + 生成物 + 校验"，不手写第二份账。

## 二、SPDX 标识符与"AI 生成、无版权"的表达

### 2.1 准确标识符

SPDX License List 3.29.0（releaseDate 2026-09-16，共 740 个许可），取自 [license-list-data/json/licenses.json](https://raw.githubusercontent.com/spdx/license-list-data/main/json/licenses.json)，与 [spdx.org/licenses](https://spdx.org/licenses/) 页面一致：

| 标识符 | 全称 | OSI | FSF Libre |
|---|---|---|---|
| `CC-BY-4.0` | Creative Commons Attribution 4.0 International | 否 | 是 |
| `CC-BY-SA-4.0` | Creative Commons Attribution Share Alike 4.0 International | 否 | 是 |
| `CC0-1.0` | Creative Commons Zero v1.0 Universal | 否 | 是 |
| `MIT` | MIT License | 是 | 是 |
| `OFL-1.1` | SIL Open Font License 1.1 | 是 | 是 |
| `Apache-2.0` | Apache License 2.0 | 是 | 是 |
| `CC-PDM-1.0` | Creative Commons Public Domain Mark 1.0 Universal | 否 | 否 |
| `CC-PDDC` | Creative Commons Public Domain Dedication and Certification | 否 | 否 |

列表里**没有**通用的"public domain"标识符（名称含 public domain 的只有 CC-PDDC、CC-PDM-1.0、PDDL-1.0 及若干机构专用条目，如 NIST-PD、NCBI-PD），`LicenseRef-PublicDomain` 也不在列表中（它只能作为自定义引用）。

复合表达式与自定义引用（SPDX 2.3 Annex D）：`AND`（"simultaneously comply with two or more licenses"）、`OR`（"a choice between two or more licenses"）、`WITH`；自定义引用语法 `["DocumentRef-"(idstring)":"]"LicenseRef-"(idstring)`，`idstring = 1*(ALPHA / DIGIT / "-" / "." )`（[SPDX 2.3 license expressions](https://spdx.github.io/spdx-spec/v2.3/SPDX-license-expressions/)）。SPDX 2.3 的 License Concluded 字段另有 `NONE`（"if the SPDX document creator concludes there is no license available for this file"）与 `NOASSERTION`（[File information](https://spdx.github.io/spdx-spec/v2.3/file-information/)）。

### 2.2 "AI 生成、无版权 / 放弃权利"怎么标

**未找到 SPDX 针对 AI 生成内容的官方说明**（查了许可列表、2.3 规范的许可表达式与文件信息章节，以及 license-list-XML 的收录原则文档）。能找到的相关一手原文来自 CC：

| 原文 | 来源 |
|---|---|
| CC0 定位："a public domain dedication for rights holders who wish to put their work into the public domain before the expiration of copyright"；PDM 定位："a tool for marking a work that is in the worldwide public domain" | [CC FAQ](https://creativecommons.org/faq/) |
| "If a work is already in the worldwide public domain, you should mark it with CC's Public Domain Mark. Note that, in some cases, a work may be in the public domain under the copyright laws of some jurisdictions but not others." | 同上 |
| "You should also not apply Creative Commons licenses to works that are no longer protected by copyright or are otherwise in the public domain."；"CC licenses are operative only when applied to material in which a copyright exists" | 同上 |
| CC0 §3 Public License Fallback：弃权若被认定无效，则授予 "royalty-free, non transferable, non sublicensable, non exclusive, irrevocable and unconditional license" | [CC0 1.0 法律文本](https://creativecommons.org/publicdomain/zero/1.0/legalcode) |

判断（推断）：

1. 项目自己生成的 AI 素材，版权状态可能因法域而异（CC FAQ 原文承认"某些法域是公有领域、另一些不是"）。`CC0-1.0` 两头都成立：有权利时放弃，放弃无效时回落为宽松许可；没有权利时声明也无害。`CC-PDM-1.0` 等于断言"在全世界都没有已知版权"，项目无法替所有法域做这个事实判断。`LicenseRef-*` 只在需要自拟文本时才用，其他工具无法识别。
2. 这与 ADR-0006 决定 9"自制素材 CC BY-SA 4.0"不同：若 AI 素材也按 BY-SA 发布，在它不受著作权保护的法域，按 CC FAQ 原文许可根本不生效。这是一个需要项目主定案的取舍（留"反圈占"的 SA 锁，还是用 CC0 如实反映权利状态），本文不替它下结论。
3. 生成服务或模型本身的使用条款可能对产物另有约束，AI 素材准入时需另行核查（本文未核实具体服务的条款）。

两个值得记下的现象：

- OpenMoji 的 `openmoji_date` 不随文件修改更新：26C8、1F62D 在 15.0.0 改过（见 4.2），日期仍是 2018、2020 年。（推断）上游的日期字段表示"创作日期"，不能当"最后修改"用；判断是否改过只能靠哈希。

### 3.2 值得借用的字段集（推断）

| 字段 | 借自 | 用途 |
|---|---|---|
| `license.spdx` + `license.title` + `license.url` | Iconify | 机器校验 + 人读 + 链接（署名页直接用） |
| `license: {type: "custom", url}` 这种兜底形态 | Simple Icons | 非 SPDX 许可必须显式标出并附原文链接 |
| `author{name,url}`，可细到单文件（`openmoji_author`） | Iconify、OpenMoji | TASL 中的 A；OpenMoji 这类多作者项目可逐文件署名 |
| `source` 必须是不可变 permalink | Simple Icons | 来源可复查 |
| `attributionText`（现成的署名句） | DiceBear `meta.license.text` | 生成 CREDITS 与应用内署名页 |
| 上游自身的语义字段（`annotation`、`cldr`、`group`） | OpenMoji、Fluent | 可选，便于人工审阅 |

本项目要**自己补**的（上游都没有）：`ref`（tag / commit SHA）、`sha256`、`upstreamSha256`、`modifications`、`kind`（fetched / generated / authored），以及 AI 素材的生成元数据（第八节）。完整示例见第十一节。

### 4.2 同码点跨版本是否被重绘（决定"钉版本"有没有实际意义）

方法：按 tag 逐个下载同一码点，比较 SHA-256；有差异的再用 sharp 0.35.4（libvips）以 288×288 栅格化，逐像素比较（任一通道差 > 8/255 计为不同）。

| 1F631 | 未测 | 未测 | `dc459697` 3,674 B | **`28018215` 3,353 B** | 同 15.0.0 | 同 | 同 |

14.0.0→15.0.0 的差异内容（`diff` 26C8 两版）：路径数据重新序列化（绝对坐标改相对坐标、省略前导 0）、删除 `stroke="none"`、颜色十六进制改小写、删除空组 `<g id="hair"/>`/`<g id="skin"/>`/`<g id="skin-shadow"/>`；26C8 另外**新增了一条 `fill="#fff"` 的路径**（雨区的白色填充）。像素比较：

| 1F62D 14.0.0 vs 15.0.0 | 190 px（0.23%），最大通道差 179 | — | — |
| 1F631 14.0.0 vs 15.0.0 | 97 px（0.12%），最大通道差 209 | — | — |
| 1F642（字节相同，对照） | 0 px | — | — |

结论：**大版本之间确有字节变化，且其中有肉眼可见的改动**（在本项目用到的 14 个 OpenMoji 文件中，14.0.0→15.0.0 变了 3 个，其中 26C8 在非白底上约 5% 像素不同）；15.0.0→17.0.0 这 14 个文件完全不变。钉版本既是哈希可复现的前提，也关系到画面一致。

**仓库现有文件对应哪个 tag**：14 个 OpenMoji 文件与 15.0.0、15.1.0、16.0.0、17.0.0 四个 tag **全部逐字节相同**；其中 11 个与 14.0.0 也相同，1F62D、1F631、26C8 与 14.0.0 不同。所以只能断定"来自 ≥15.0.0"，**事后靠哈希无法判定是哪一个 tag**——这正说明版本必须在拉取当时写进 manifest，事后只能反推出一个版本区间。（推断）若钉 17.0.0，重取的字节与现有文件完全一致。

## 五、优化/压缩与"未修改"的许可边界

### 5.1 法律文本原文（CC BY 4.0 / CC BY-SA 4.0）

条款编号两份许可不同：CC BY 4.0 的 Licensed Material 在 §1(f)，CC BY-SA 4.0 在 §1(h)（BY-SA 多了 "BY-SA Compatible License" 与 "License Elements" 两条定义）；其余引用条款号相同。以下引自 CC 官网法律文本；BY 4.0 条文与 Twemoji 随附的 `LICENSE-GRAPHICS` 全文核对过，BY-SA 4.0 的条款编号用 OpenMoji 随附的 `LICENSE.txt` 核对过。

| 条款 | 原文 | 来源 |
|---|---|---|
| §1(a) Adapted Material | "material subject to Copyright and Similar Rights that is derived from or based upon the Licensed Material and in which the Licensed Material is translated, altered, arranged, transformed, or otherwise modified in a manner requiring permission under the Copyright and Similar Rights held by the Licensor." | [BY 4.0](https://creativecommons.org/licenses/by/4.0/legalcode)、[BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/legalcode) |
| §1(f)（BY）/ §1(h)（BY-SA）Licensed Material | "the artistic or literary work, database, or other material to which the Licensor applied this Public License." | 同上 |
| §2(a)(4) 技术性修改 | "The Licensor authorizes You to exercise the Licensed Rights in all media and formats whether now known or hereafter created, and to make technical modifications necessary to do so. … For purposes of this Public License, simply making modifications authorized by this Section 2(a)(4) never produces Adapted Material." | 同上 |
| §3(a)(1) 署名义务 | "If You Share the Licensed Material (including in modified form), You must: … B. indicate if You modified the Licensed Material and retain an indication of any previous modifications; and C. indicate the Licensed Material is licensed under this Public License, and include the text of, or the URI or hyperlink to, this Public License." | 同上 |
| §3(b) ShareAlike（仅 BY-SA） | "if You Share Adapted Material You produce, the following conditions also apply. 1. The Adapter's License You apply must be a Creative Commons license with the same License Elements, this version or later, or a BY-SA Compatible License. …" | [BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/legalcode) |

注意两点（文本如此）：① **"标明修改"（§3(a)(1)(B)）的触发条件是"You modified"，不以构成 Adapted Material 为前提**；② ShareAlike（§3(b)）只在分享 Adapted Material 时触发。4.0 法律文本没有定义 "Collection"（对 OpenMoji 附带的 BY-SA 4.0 全文 grep 无命中），汇编规则只见于 FAQ（见 6.5）。

### 5.3 对具体操作的判断（推断）

以下是依据 5.1、5.2 原文作出的**推断，不是法律意见**；FAQ 明说"是否构成改编主要取决于适用的著作权法"。

| 操作 | 构成 Adapted Material？（推断） | 需要标"已修改"？（推断） | 理由 |
|---|---|---|---|
| 字节原样复制（钉版拉取后原样入库，即已定方向） | 否 | 否 | 只是复制与分享；且"未修改"可由 `sha256(文件) == sha256(上游@钉住版本)` 机器证明 |
| SVGO 压缩（删空白/空组、降数字精度、改相对坐标） | 通常否：没有新的创造性表达，接近 FAQ 所说的 "formatting changes" | **建议标**：它不是 §2(a)(4) 所说"为在某媒介/格式行使权利所**必要**"的修改（原文件浏览器本就能渲染），也难说一律属于 FAQ 的 "trivial alterations"——降精度会改几何；4.2 中 OpenMoji 14→15 的重新序列化就伴随了像素级差异 | 标注成本几乎为零（manifest 记一条 `modifications`，CREDITS 汇总一句"部分文件经自动压缩，未作有意的视觉改动"），可消除争议 |
| 改 `width`/`height` 属性 | 否 | 可不标（接近 "changing a font size" 类的琐碎改动），但它会破坏"与上游哈希一致"的机器可证性 | 更好的做法是不改文件、用 CSS 或 `<img width>` 控制尺寸，零修改 |
| 包进 `<symbol>` sprite | 汇编而非改编（见 6.5 FAQ 与 wiki） | **需标**（技术性封装）：OpenMoji 每个文件都用 `id="emoji"`、`id="color"`、`id="line"`，放进同一文档必须改写 id，字节层面确有修改 | sprite 文件成为多作品文件（许可表达式 `CC-BY-SA-4.0 AND CC-BY-4.0`），仍须逐作品署名；已定方向本期不做 sprite |
| 光栅化（SVG→PNG/WebP） | 否（FAQ："any format or medium … not considered adaptations"） | 建议注明"由 SVG 转为 PNG"（类比 wiki 的 "Cropped from original"） | 格式转换本身不触发 SA |
| 改色、重绘局部、裁切、与其他图合成 | 改色/重绘/合成**很可能**构成（有新的表达选择）；单纯裁切未必 | **需标**，并保留原署名与之前的修改记录 | 对 BY-SA 素材（OpenMoji），分享改编物时须以 BY-SA 4.0 或兼容许可（含 GPLv3，见 6.5）发布 |

对管线的含义（推断）：已定方向"进仓库的字节 = 上游字节、暂不做 SVGO/sprite"让"未修改"成为一个可机器验证的事实，而不是 CREDITS.md 里的一句人工声明。将来一旦引入任何处理，manifest 必须把"上游原始哈希"和"交付文件哈希"分开记录，并附修改说明——这样第三问"有没有被改过"才依然可答。

### 6.4 现状实测：部署产物里没有任何署名

方法：2026-09-23 在当前 HEAD（`b187d9d`）执行 `npm ci && npx vite build`，对 `dist/index.html`、`dist/assets/*.js`、`dist/assets/*.css` 逐一 grep `OpenMoji`、`openmoji.org`、`Twemoji`、`CC BY`、`CC-BY`、`creativecommons`、`CREDITS`：**全部 0 命中**。`src/` 中也没有指向 CREDITS.md 或仓库的链接（grep `href=` 无命中）；SVG 文件本身不含元数据（见 4.1、4.3）。也就是说，家庭打开网站拿到的是一批 CC 许可文件，交付物里一个署名字符都没有；署名只存在于 GitHub 仓库的 CREDITS.md，而网站并不链接它。

判断（推断）：

1. **仅在源码仓库的 CREDITS.md 署名，对 Pages 这条分发链路不够。** §3(a)(2) 的"合理"是相对"You Share 的媒介、方式与情境"而言的；家长通过网页应用拿到素材，却无从得知 CREDITS.md 的存在。CC wiki 也提醒，用户看不到的地方（如元数据）不应是唯一的署名位置。
2. 连 Twemoji 放得最宽的标准——"a mention in the HTML/JS source"——现有构建产物也没达到。
3. 最稳妥的做法：**应用内设一个可达的"素材署名"页**（家长区"关于"之类的位置，符合 Twemoji 说的 'About' section、OpenMoji 说的 'About' section），内容随构建打包、不发任何网络请求，列出 TASL 与许可链接（链接只作文本、用户点击才跳转）。§3(a)(2) 的例子也允许"链接到一个包含所需信息的资源"，所以链到 GitHub 上的 CREDITS.md 在许可层面也成立；但那需要离开应用，且依赖外部站点可用，不如应用内页面自足。
4. 仓库本身也是一条分发链路（`public/assets/` 公开可下载），CREDITS.md 与许可全文继续承担这条链路的署名。

### 7.3 一个会悄悄破坏"字节 = 上游字节"的仓库设置：`.gitattributes`

仓库 `.gitattributes` 为 `* text=auto eol=lf`，另有 `*.png binary`、`*.jpg binary`、`*.woff2 binary`。git 文档原文：`text=auto` 时 "Git decides by itself whether the file is text or binary. If it is text and the file was not already in Git with CRLF endings, line endings are converted on checkin and checkout"；"Unsetting the text attribute on a path tells Git not to attempt any end-of-line conversion upon checkin or checkout"；内置宏 `binary` 等价于 `-diff -merge -text`（[gitattributes](https://git-scm.com/docs/gitattributes)）。

只读实测（2026-09-24，git 2.55.0.windows.3，`git hash-object` 不带 `-w`，不写入任何对象；`--path` 按该路径的属性套用过滤器，`--no-filters` 按原样计算，见 [git-hash-object](https://git-scm.com/docs/git-hash-object)）：

| 文件 | CR / LF 个数 | 原样 blob 哈希 | 按 `public/assets/…` 路径过滤后的 blob 哈希 | 结论 |
|---|---|---|---|---|
| FxEmoji `u1F600-grin.svg`（上游原样） | 33 / 33（CRLF） | `d1e0434d…` | `5893c486…` | **提交时会被改成 LF**：SHA-256 从上游的 `253bd508…` 变成 `878b1ddd…` |
| OpenMoji 26C8（15.1.0） | 0 / 23 | `84e98c22…` | `84e98c22…` | 不变 |

另：`git check-attr` 显示 `public/assets/**/*.webp` 为 `text: auto`（没有 binary 规则，靠 git 自动识别），`*.png` 为 `binary: set`。现有 24 个文件都没有 CR（逐一实测 CR=0），所以目前没出事；一旦接入 FxEmoji 这类 CRLF 上游，"进仓库的字节 = 上游字节"就会被 git 在提交时静默打破。（推断）应给素材目录单独加规则，例如 `public/assets/** -text`（或 `binary`），并把 `.webp`/`.avif` 纳入 binary；哈希校验（第十二节第 3 条）会在这种情况下变红，正好兜底。

### 7.4 不变量清单

`check:assets` 应验证的完整不变量清单见第十二节（推断）。其中直接来自上面事实的几条：每个文件都在 manifest 里、每条 manifest 都有文件（OpenMoji 式双向存在性）；SHA-256 一致（兜住 7.3 的 EOL 改写与 4.8 的 jsDelivr 版本回退）；fetched 条目的 ref 必须是不可变的 tag 或 40 位 SHA（Simple Icons 式 permalink 规则）；许可必须在白名单里、用合法 SPDX 标识符。

### 8.1 C2PA：支持哪些格式、怎么嵌

C2PA Specification 2.2（版本记录 "2.2 - May 2025"），[spec.c2pa.org](https://spec.c2pa.org/specifications/specifications/2.2/specs/C2PA_Specification.html)（c2pa.org 旧地址 301 跳转至此）。

### 8.3 构建与重编码对溯源信息的影响（实测）

**Vite 复制 public/**：文档原文 "Assets in this directory will be served at root path `/` during dev, and copied to the root of the dist directory as-is."（[Vite 静态资源](https://vite.dev/guide/assets)）。实测（2026-09-23，vite 6，当前 HEAD 执行 `npx vite build`）：`public/assets/` 的 24 个文件与 `dist/assets/` 下对应文件 SHA-256 **24/24 完全相同**。

**重编码是否丢元数据**（2026-09-23/24，sharp 0.35.4，libvips；逐块解析 PNG 检查）：输入是一张 PNG，含 A1111 风格的 `tEXt` 块 `parameters`（含 seed 等参数），以及一个 `iTXt` XMP 块，内容为 `Iptc4xmpExt:DigitalSourceType = …/trainedAlgorithmicMedia`。

| 处理 | `parameters`（生成参数） | XMP（Digital Source Type） | 输出里的块 |
|---|---|---|---|
| PNG→PNG，默认 | **丢失** | **丢失** | IHDR pHYs IDAT IEND |
| PNG→WebP，默认 | **丢失** | **丢失** | — |
| PNG→WebP，`keepMetadata()` | **丢失**（cwebp 文档列出的可携带元数据只有 exif、icc、xmp 三类） | 保留 | — |
| PNG→PNG，`keepMetadata()` | 保留，但被改写为压缩的 `zTXt` | 保留，同样改写为 `zTXt` | IHDR eXIf pHYs zTXt zTXt IEND |

Google 的 cwebp 同样默认丢弃："-metadata … Valid values: `all`, `none`, `exif`, `icc`, `xmp`. The default is `none`."（[cwebp 文档](https://developers.google.com/speed/webp/docs/cwebp)）。（推断）任何重编码都会改变字节，所以即便把 C2PA 清单搬到新文件里，基于哈希的 hard binding 也对不上；而 PNG 的 `caBX` 被规范标为 "not safe to copy"。结论：**溯源信息不能指望跟着文件走，必须记在 manifest 里，并保留"生成器原始输出"的哈希。**

手头没有 AI 生成图，这里用两类代理样本（2026-09-24，sharp 0.35.4）：带渐变光影的 Fluent 3D PNG 原件（256²）、把渐变丰富的 Fluent Color SVG 与平涂的 OpenMoji 26C8 栅格化到目标尺寸。

| 样本 | PNG | WebP 无损 | WebP 有损 q80 | AVIF q50 |
|---|---|---|---|---|
| Fluent 3D 原件 256²（原文件 52,131 B） | 75.7 KB（sharp 重压，比原件大） | 33.5 KB | 6.7 KB | 6.1 KB |
| Fluent Color → 512² | 123.2 KB | 64.2 KB | 11.2 KB | 8.3 KB |
| Fluent Color → 1024² | 329.1 KB | 177.7 KB | 24.3 KB | 15.9 KB |
| OpenMoji 26C8 → 1024²（平涂） | 38.7 KB | 21.6 KB | 18.5 KB | 11.3 KB |

Google 官方口径："WebP lossless images are 26% smaller in size compared to PNGs"；"lossy WebP also supports transparency, typically providing 3× smaller file sizes compared to PNG"（[WebP 概述](https://developers.google.com/speed/webp)）。（推断）真实 AI 图带纹理和噪点，压缩率通常不如上面这些由矢量渲染出的干净样本，实际体积可能明显更大；AI 素材进库前应按真实样本复测。

## 十一、建议的 manifest 结构（推断）

**本节为建议（推断）**。设计要点：来源与许可在 `sources` 里只声明一次，条目引用（对应第十二节第 7 条）；`fetched` 条目靠"来源 + 不可变 ref + 上游路径"可重取，靠哈希核对；`authored` 条目（自制与 AI）不可重取，只靠哈希钉住，并带生成元数据。下例中 OpenMoji、Twemoji 两条的 commit 与哈希是本文实测值（OpenMoji 17.0.0 的 commit 即 npm `gitHead`，Twemoji v17.0.3 同理；两个文件在这两个 tag 下的字节与仓库现有文件相同），其余为占位。

## 十二、check:assets 应验证的不变量（推断）

**本节全部为建议（推断）**，依据分别标在"依据"列。编号 1–10 建议进 `npm run check`（离线、确定）；11–14 为可选或放到拉取脚本里做。

| # | 不变量 | 红了意味着 | 依据 |
|---|---|---|---|
| 1 | **目录全覆盖**：`public/assets/**` 下每个文件在 manifest 里恰有一条记录（按相对路径匹配） | 有文件答不出"来自哪里" | 已定方向"三问答不上就红"；OpenMoji 测试的数据↔文件存在性（7.2） |
| 2 | **无悬空记录**：manifest 每条记录指向的文件都存在 | 清单与仓库脱节 | 同上（反方向） |
| 3 | **哈希一致**：`sha256(文件字节) == 记录.sha256` | 文件被改过，或被 git EOL 规则改写（7.3），或拉取时拿到 CDN 回退的旧版本（4.8） | 已定方向"有没有被改过"；Simple Icons 的"文件内容与数据逐字相等"（7.2） |
| 4 | **来源可追**：`fetched` 条目必须有 `source`（登记在来源表里）、`ref`（tag 或 40 位 commit SHA，禁止分支名、`latest`、版本区间）与上游路径；`generated` 条目必须有生成器名称 + 精确版本 + seed/options；`authored` 条目必须有作者（或 AI 生成元数据，见第八节）与创建日期 | 来源可变或不可复查 | Simple Icons 的 permalink 规则（7.2）；4.2 证明大版本间字节会变 |
| 5 | **许可白名单**：`license` 是合法 SPDX 表达式，且每个标识符都在项目白名单内（如 `CC-BY-4.0`、`CC-BY-SA-4.0`、`CC0-1.0`、`MIT`、`Apache-2.0`、`OFL-1.1`；`LicenseRef-*` 须在白名单中逐个登记并附许可文本） | 许可不明或未审过 | Simple Icons `checkLicense`（7.2）；SPDX 列表（第二节） |
| 6 | **NC 隔离**：许可含 NC 元素的条目必须位于 `public/assets/nc/<来源>/`；`nc/` 下的条目也必须是 NC | ADR-0006 决定 10 被绕过 | ADR-0006 决定 10 |
| 7 | **来源↔目录↔许可一致**：路径里的来源目录名（`openmoji`、`twemoji`、`original` …）与记录的 `source` 一致；许可在来源表里声明一次，条目继承（条目要覆盖时必须显式写明理由） | 逐条手抄许可出错 | 4.5：聚合方（Iconify）把 FxEmoji 许可写错的实例 |
| 8 | **修改标记自洽**：对 `fetched` 条目，`sha256 ≠ upstreamSha256` 当且仅当 `modifications` 非空 | "未修改"声明与事实不符 | CC 4.0 §3(a)(1)(B)（第五节） |
| 9 | **代码引用存在**：`src/game/emotions.ts` 等处引用的每个素材路径都存在且在 manifest 中（可在 vitest 里直接 import `ALL_VARIANTS`/`SCENES` 逐一检查） | 运行时 404、界面缺图 | 现状：`rounds.test.ts` 只用正则校验路径形状，不校验文件存在 |
| 10 | **署名由清单生成**：CREDITS.md（以及应用内署名页的数据）由 manifest 生成；check 时重新生成并与仓库内文件逐字比对 | 署名与清单漂移 | 与 `check-disclaimer.mjs`"单一来源 + 机器校验"同构（ADR-0006 决定 13）；第六节"应用内署名"判断 |
| 11 | **check 离线**：`check:assets` 只读本地文件，不联网；与上游的在线比对放进拉取脚本的 `--verify` 模式，人工或每期收口时运行 | CI 结果受网络与上游状态影响 | 4.8 限额与 CDN 行为 |
| 12 | **SVG 不含脚本与外部引用**：不出现 `<script>`、`<foreignObject>`、事件属性（`on*=`），`href`/`xlink:href` 不指向 `http(s)://`；命名空间与 DTD 声明中的 URL 除外 | 素材文件成为运行时网络请求或脚本的入口 | 零收集红线（CONTRIBUTING："运行时除自身静态资源外必须零网络请求"） |
| 13 | （可选）**光栅元数据策略**：AI 光栅文件的 PNG 文本块、EXIF/XMP 是否保留，与 manifest 声明的策略一致 | 生成参数意外随文件公开，或该保留的溯源信息被剥掉 | 第八节 |
| 14 | （可选）**体积预算**：单文件与总量设上限 | 静态站体积失控 | 第九节估算 |

另外两条工程性约束（推断）：manifest 本身按 JSON Schema 校验、禁止未知字段（Simple Icons 的 `additionalProperties: false`）；条目按路径排序，便于 diff 与审阅。
